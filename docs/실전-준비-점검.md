## 🔴 치명

### 1. 주문이 실패해도 "샀다"고 기록한다

**현재 상태**

`pyupbit`의 주문 메서드는 **실패해도 예외를 던지지 않는다.** 내부적으로 이렇게 되어 있다:

```python
# pyupbit/exchange_api.py — buy_market_order / sell_market_order 공통
except Exception as x:
    print(x.__class__.__name__)
    return None          # ← 실패가 None 으로 조용히 반환된다
```

API가 거부한 경우(잔고 부족, 최소금액 미달, IP 미등록 등)는 `{"error": {...}}` dict를 준다.

그런데 `upbit/live.py:214-221` 은 반환값을 **검사하지 않는다**:

```python
action, order = "buy", self.buy(price)   # order 가 None 이어도
...
state["position"] = 1 if action == "buy" else 0   # 무조건 '보유'로 기록
```

**실제로 재현했다**

거래소 클라이언트를 실패(`None` 반환)하도록 바꿔 `step()`을 돌린 결과:

```
주문 전 상태: 0
   [거래소] 주문 실패 → None 반환
주문 반환값: None
주문 후 상태: 1        ← 안 샀는데 샀다고 기록
```

**무슨 일이 벌어지나**

봇은 없는 코인을 들고 있다고 믿는다. 그래서 —
- 매수 신호가 다시 와도 "이미 보유 중"이라 안 산다 → 상승을 통째로 놓친다
- 매도 신호가 오면 팔 게 없어 주문이 또 실패한다
- 이 어긋남은 **사람이 손으로 고치기 전까지 영구히 지속된다**

**✅ 어떻게 고쳤나**

pyupbit 공개 주문 메서드를 아예 쓰지 않는다. `upbit/exchange.py` 에서 내부 요청
함수(`_call_post`/`_call_get`)를 직접 호출해 **타입별 예외를 살리고 타임아웃을 건다**
(pyupbit 공개 메서드에는 타임아웃이 아예 없다 — `exchange_api.py` 에 `timeout` 등장 0회).

오류를 4가지로 분류해 각각 다르게 대응한다:

| 분류 | 뜻 | 대응 |
|---|---|---|
| `OrderRejected` | 거래소가 거부 (잔고부족·최소금액) | 주문은 확실히 안 들어감. 상태 안 바꿈 |
| `AuthError` | 키 만료·IP 미등록·권한 부족 | **즉시 봇 중단.** 계속 시도하면 계정 차단 |
| `RateLimited` | 요청 한도 초과 | 이번 주기 건너뛰기 |
| `UnknownOutcome` | 타임아웃 — 들어갔는지 모름 | 성공/실패 어느 쪽으로도 기록 안 함. 다음 사이클에 잔고로 확인 |

그리고 주문 성공 ≠ 체결이므로 `get_order` 로 폴링해 실제 체결을 확인한 뒤에만
기록한다. 부분 체결이면 체결된 만큼만 반영한다.

### 2. 실제 잔고와 대조하지 않는다

**현재 상태** — `upbit/live.py:202`

```python
held = int(state.get("position", 0))   # 파일에 적힌 값만 믿는다
```

거래소에 실제로 뭘 들고 있는지 **한 번도 확인하지 않는다.**

**무슨 일이 벌어지나**

상태파일과 실제가 어긋나는 경로가 많다:
- 항목 1의 주문 실패
- 사람이 앱에서 직접 매도
- 봇을 두 개 돌림 (항목 4)
- 상태파일 삭제 / 다른 폴더에서 실행
- 부분 체결

어긋나면 봇의 모든 판단이 틀린 전제 위에서 돌아간다.

**✅ 어떻게 고쳤나**

포지션을 매 사이클 **실제 잔고에서 읽는다**. 상태파일에는 거래소가 모르는 것
(진입가, 손절선, 재진입 차단 플래그)만 남긴다.

불일치가 있으면 경고하고 실제 잔고에 맞춘다:
- 잔고에 코인이 있는데 진입 기록이 없다 → 현재가를 진입가로 간주 (수동 매수했거나 상태파일 유실)
- 진입 기록이 있는데 잔고가 비었다 → 기록을 지운다 (수동 매도했거나 주문이 실제로는 실패)

### 3. 손절이 실전에 전혀 연결되어 있지 않다

**현재 상태**

`upbit/risk.py`(손절/익절/추적손절)는 **백테스터에서만** 쓰인다.
`upbit/live.py`에는 `risk` 라는 단어조차 없다:

```
$ grep -n "risk\|RiskRules\|stop" upbit/live.py
  (결과 없음)
```

**무슨 일이 벌어지나**

이게 제일 위험하다. **백테스트로 검증한 전략과 실제로 도는 전략이 다르다.**

`docs/실험기록.md`에서 "ATR×2 추적손절로 MDD를 -19.7% → -14.0%로 줄였다"는
결과를 보고 실전에 넣으면, 봇은 **손절 없이** 돈다. 검증한 적 없는 전략이
내 돈을 굴리는 셈이다.

**✅ 어떻게 고쳤나**

`Trader` 가 `RiskRules` 를 받아 진입가·손절선을 저장하고, 매 사이클 확인해
**전략 신호보다 우선** 적용한다. 추적 손절선 갱신과 손절 후 재진입 차단도
백테스터와 같은 규칙으로 동작한다.

> ⚠️ **남는 한계**: 백테스트는 봉의 **저가**로 손절을 판정하지만, 실전은 확인
> 시점의 **현재가**로만 본다. 봉 중간의 급락은 놓친다.
> 일봉으로 돌리면 하루 한 번만 확인하므로 그 사이 -20% 가 빠져도 다음 확인
> 때까지 모른다. **실전 성적이 백테스트보다 나쁠 수 있는 구조적 이유다.**
>
> 줄이려면: 더 짧은 주기로 확인하거나(별도 손절 감시 루프), 거래소에
> 예약주문(stop order)을 걸어두는 방법이 있다. 지금은 둘 다 미구현.

### 4. 중복 실행을 막지 않는다

**현재 상태** — 아무 잠금도 없다. 터미널 두 개에서 `05_live.py`를 돌리면 둘 다 돈다.

**무슨 일이 벌어지나**

둘 다 매수 신호를 보고 각자 주문 → **의도한 금액의 2배**가 들어간다.
`UPBIT_MAX_ORDER_KRW` 상한은 1회 주문 기준이라 이걸 못 막는다.
cron에 걸어두고 실행이 밀리면 자동으로 발생할 수 있다.

**✅ 어떻게 고쳤나**

`upbit/lock.py` — PID 락 파일. 살아있는 프로세스가 잡고 있으면 즉시 종료한다.
죽은 프로세스가 남긴 낡은 락은 자동 인계받는다(그것 때문에 봇을 영영 못 켜면
그것도 문제이므로). 남의 락은 지우지 않는다.

## 🟠 중요

### 5. 봉 마감 시각에 맞춰 돌지 않는다

**현재 상태** — `scripts/05_live.py:115-118`

```python
for _ in range(args.every):   # 시작 시각부터 상대적으로 N초 대기
    time.sleep(1)
```

**문제**

일봉 전략인데 `--every 86400`으로 돌리면, 봇을 켠 시각 기준으로 24시간마다 돈다.
업비트 일봉은 **09:00 KST**에 마감된다. 15시에 켰으면 매일 15시에 판단하는데,
그때 최신 확정봉은 6시간 전 것이다. 신호가 하루씩 밀린다.

백테스트는 "봉 마감 직후 판단"을 가정했으므로 **다른 전략이 된다.**

**✅ 어떻게 고쳤나**

`upbit/schedule.py` — `--loop` 의 **기본이 봉 마감 정렬**이 됐다.
업비트 기준 일/주/월봉은 09:00 KST, 분봉은 분 경계에 마감된다.
로컬 시간대에 의존하면 서버 위치에 따라 결과가 달라지므로 KST를 고정해 계산한다.
마감 직후엔 API에 확정봉이 아직 없을 수 있어 30초 기다린다.
(`--every N` 을 주면 예전처럼 상대 주기로도 돌 수 있다)

### 6. API 오류를 유형별로 다루지 않는다

**현재 상태** — `scripts/05_live.py:110`

```python
except Exception as e:   # 전부 뭉뚱그려 잡고 계속 진행
```

`pyupbit`은 구체적인 예외를 제공하는데 하나도 안 쓰고 있다:
`TooManyRequests`, `InsufficientFundsBid`, `UnderMinTotalBid`,
`NoAutorizationIP`, `ExpiredAccessKey`, `JwtVerification`, `NonceUsed`

**문제**

- **레이트리밋**(`TooManyRequests`): 바로 재시도하면 더 오래 막힌다 → 지수 백오프 필요
- **인증 오류**(`ExpiredAccessKey`, `NoAutorizationIP`): 계속 시도하면 계정이 차단될 수 있다 → 즉시 중단해야 함
- **일시적 네트워크 오류**: 재시도하면 되는데 지금은 그냥 다음 주기까지 아무것도 안 함

**⚠️ 부분 해결**

오류 분류와 대응은 구현했다(항목 1 표 참고) — 인증 오류는 즉시 중단,
레이트리밋은 이번 주기 건너뛰기, 거래소 오류는 로그 남기고 계속.

**하지만 지수 백오프 재시도는 아직 없다.** 레이트리밋이나 일시적 네트워크
오류가 나면 이번 주기를 통째로 건너뛴다. 일봉이면 하루를 날리는 셈이다.

### 7. 부분 체결과 먼지(dust)를 처리하지 않는다

시장가 매도는 소수점 잔량을 남길 수 있다. 그 잔량의 평가액이 5,000원(업비트 최소
주문금액) 미만이면 **영원히 못 판다**. 잔량이 남았는데 상태는 "현금"이 되어
다시 매수하면 조금씩 쌓인다.

**✅ 어떻게 고쳤나 — 그리고 모의로 돌리다 진짜 버그를 찾았다**

업비트 최소 주문금액 5,000원으로 사면 **수수료를 떼고 4,997원어치가 남아
그 즉시 매도 불가능한 먼지가 된다.** 봇은 이걸 '현금'으로 보고 또 사서
먼지를 쌓는다. 모의로 실행해보고 나서야 발견했다.

- 주문 하한을 5,500원(`MIN_SAFE_ORDER_KRW`)으로 올렸다 — 수수료와 약 5% 하락까지 버틴다
- 먼지가 있으면 매 사이클 경고한다
- 먼지는 '팔 수 없으므로 포지션 아님'으로 본다. 다음 매수 때 합쳐지면 다시 팔 수 있다

### 8. 긴급 정지 수단이 없다

봇이 이상하게 동작하거나 시장이 급변할 때 **"지금 당장 다 팔고 멈춰"** 할 방법이 없다.
`Ctrl+C`는 봇만 멈추고 포지션은 그대로 남는다.

**✅ 어떻게 고쳤나**

`--panic-sell` — 전량 매도 후 종료. 재진입을 막아둔다(급한 상황에 껐다 켰다고
바로 다시 사면 곤란하다). 전략이 한 번 현금 신호를 내야 풀린다.

## 🟡 권장

### 9. API 키 권한 최소화가 문서화되어 있지 않다

`pyupbit.Upbit`에는 **`withdraw_cash`, `withdraw_coin`** 메서드가 있다.
출금 권한이 있는 키가 유출되면 **자산을 통째로 인출당한다.**

지금 `.env.example`과 README는 "키를 커밋하지 마라"만 말하고,
**어떤 권한으로 발급해야 하는지**는 말하지 않는다.

**✅ 어떻게 고쳤나**

`.env.example` 맨 위에 명시했다 — 출금 권한 절대 미체크, IP 화이트리스트 등록 필수.
그리고 봇 시작 시 키 만료일을 확인해 7일 이내면 경고한다
(만료되면 봇이 조용히 멈추고 포지션이 방치된다).

### 10. 실제 체결 기록이 없다

지금 남는 건 `reports/trades.log`(텍스트 로그)뿐이다.
**실제 체결가·수수료·슬리피지**를 구조화해 남기지 않는다.

이게 있어야 "백테스트에서 가정한 슬리피지 0.05%가 실제와 맞나"를 검증할 수 있다.
실측이 0.2%면 백테스트 수익률은 전부 다시 계산해야 한다.

**✅ 어떻게 고쳤나** — `upbit/journal.py` 가 주문마다 `reports/fills.csv` 에
판단 시점 가격·실제 체결 평균가·**실측 슬리피지**·수수료율을 남긴다.
매수는 비싸게 샀을 때, 매도는 싸게 팔았을 때 양수가 되도록 부호를 통일해서
평균이 '손해 본 정도'로 읽힌다. `--status` 로 요약을 본다.

### 11. 알림이 없다

봇이 죽었는지, 주문이 나갔는지, 손절이 터졌는지 모른다. 로그를 봐야만 안다.

**✅ 어떻게 고쳤나** — `upbit/notify.py`. 웹훅(Slack/Discord) 하나로 주문 체결·
손절 발동·인증 오류 중단을 알린다. `UPBIT_WEBHOOK_URL` 이 없으면 조용히 넘어간다.
**알림 실패는 절대 봇을 멈추지 않는다** — 알림이 안 갔다고 포지션이 방치되면
본말전도다. (테스트를 쓰다 실제 버그를 잡았다: 잘못된 URL이면 `Request` 생성에서
`ValueError` 가 그대로 올라와 체결 때마다 봇이 죽었다)

### 12. 실전 경로를 테스트할 방법이 없다

현재 테스트 70여 개는 백테스트·안전장치를 검증하지만,
**실제 주문 흐름**(체결 확인, 잔고 대조, 재시도)은 검증하지 못한다.
실제 돈으로 처음 돌려보는 게 첫 테스트가 되면 안 된다.

**✅ 어떻게 고쳤나**

`upbit/fake_exchange.py` — 주문 실패·부분체결·미체결·타임아웃·슬리피지를
마음대로 주입할 수 있는 가짜 거래소. `Exchange` 프로토콜을 만족하므로
봇은 진짜와 구분하지 못한다.

특히 **`UnknownOutcome` 을 '예외는 나는데 주문은 실제로 체결됨'으로 재현**한다.
이게 있어야 "타임아웃 후 재주문하면 두 번 산다"를 테스트로 막을 수 있다.

그리고 모의(dry-run) 모드가 `PaperExchange` 로 바뀌었다 — **실제 시세**로 움직이는
가상 계좌를 상대로 **실전과 완전히 같은 주문 경로**를 탄다. 주문 흉내가 아니라
진짜 페이퍼 트레이딩이다. 그래야 모의에서 검증한 게 실전에서도 유효하다.

## 그래도 남는 한계

정직하게 적어둔다. 위를 다 했다고 안전해진 게 아니다.

1. **봉 중간 급락은 손절이 못 잡는다** (항목 3)
   일봉으로 돌리면 하루 한 번만 확인한다. 그 사이 급락하면 다음 확인 때까지 모른다.
   백테스트(봉 저가로 판정)보다 실전이 나쁠 수 있는 구조적 이유.

2. **지수 백오프 재시도가 없다** (항목 6)
   (단, launchd 의 StartCalendarInterval 은 컴퓨터가 자던 사이의 실행을 깨어난 뒤 따라잡아 준다)
   레이트리밋이나 일시적 오류가 나면 이번 주기를 통째로 건너뛴다.

3. **pyupbit 내부 구조에 의존한다**
   공개 메서드가 오류를 삼키고 타임아웃도 없어서 내부 함수를 직접 부른다.
   버전을 `pyupbit==0.2.34` 로 고정하고, 구조가 바뀌면 **시작할 때 죽는다**
   (조용히 틀리는 것보다 낫다). 올릴 땐 `UpbitExchange._check_compatibility` 확인.

4. **시계 동기화를 확인하지 않는다**
   업비트 JWT는 시각 오차에 민감하다(`nonce_used`). NTP가 꺼져 있으면 인증이 흔들린다.

5. **전략 자체가 검증되지 않았다** ← 제일 중요
   코드가 안전해진 것과 전략이 돈을 버는 건 완전히 별개다.
   `docs/실험기록.md` 의 워크포워드 결과를 보면 구간마다 최적 파라미터가 다르고
   검증 구간 성적이 들쭉날쭉하다. **인프라를 다졌다고 전략이 좋아지지 않는다.**
